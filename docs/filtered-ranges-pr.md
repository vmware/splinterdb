Allow range iterators to apply an exact key predicate, with optional routing-filter branch pruning. The new `splinterdb_iterator_init_with_filter()` and `splinterdb_iterator_init_with_bounds_and_filter()` take separate predicate, context and representative-key arguments. A predicate alone scans all relevant branches; a representative routing key requires a predicate and asserts hash compatibility under every seed. Pruning without a predicate returns `EINVAL`.

Rejected keys are skipped before application merge/finalize callbacks, preserving complete update histories for accepted keys even when routing filters admit collisions. The iterator owns its routing-key copy across trunk spans, direction changes and thread handoff; predicate context remains caller-owned. Ordinary iterator APIs remain unchanged and do not allocate filter state. No callback is added to `data_config`.

Validation: debug/release each passed 70 unit cases and four functional filter cases after merging main `0fa3bd6c`. Fifteen focused ASan cases passed before that merge. A separate combination with disk-format passed 125 unit cases per mode and the functional filter suite, including saved seeds 11/22 under current default99, six-seed cache replacement, full-width collisions, noncommutative updates, and copied-key ownership after a new seed is encountered.

Serialized real-disk benchmarks pass all result checks. Ordinary scans have overlapping sample ranges with main; eight-reader short-range throughput changes -0.18% resident and -0.30% on disk. In the selective tenant workload, predicates reduce latency 3.7–16.2% versus application filtering, and optional pruning reduces it 14.2–32.1%, including deliberate full-width hash collisions. This is workload-specific screening, not proof of neutrality; no fresh write-throughput matrix was run.
